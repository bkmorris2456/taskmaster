# Taskmaster architecture

Status: Phase 6 database infrastructure implemented and locally native-Supabase certified. Product semantics are in SPEC.md. Phases 1–5 remain intact. Auth UI and client sync remain future work.

## System and responsibilities

Static host → React SPA → Dexie/IndexedDB. A foreground synchronization coordinator exchanges commands and change pages with Supabase PostgreSQL RPCs under Supabase Auth JWTs. Supabase Auth handles password, email verification, sessions and native TOTP. A service worker caches only public app assets. No custom backend, CRDT framework, remote state cache or separate search service is necessary.

| Module                                                 | Responsibility                                                                           |
| ------------------------------------------------------ | ---------------------------------------------------------------------------------------- |
| app                                                    | boot, identity boundary, routing, error boundaries, service-worker update coordination   |
| domain                                                 | pure task rules, recurrence/date arithmetic, versioned filters and deterministic sorting |
| features/tasks, categories, views, history, auth, sync | use cases and UI; shared accessible primitives remain small                              |
| data/local                                             | Dexie schema/migrations, transactions, repositories and reactive subscriptions           |
| data/remote                                            | typed Supabase adapter, protocol encoding and error classification                       |
| sync                                                   | durable command processing, pull cursor, reconciliation and conflict records             |

Components never call Supabase for task writes. Domain commands flow through a local service; domain code has no React or network dependency. Repository interfaces exist only where meaningful testing or adapter boundaries need them. React state holds transient UI state, not a second authoritative task database. Share TypeScript protocol types and recurrence test fixtures; PostgreSQL independently enforces invariants. Test parity rather than assuming TS code executes on PostgreSQL.

## Cloud model and boundaries

Use categories, groups, tasks, recurrence_series, completion_events, sync_receipts, sync_changes and a private per-owner sync_state counter/lock row. All business rows carry owner, UUID, revision and timestamps/tombstones as defined in SPEC.md. Completion/reversal events are append-only through commands; identity and metadata snapshots survive tombstones. Series links to active task and tasks reference series; deferred constraints/transaction validation handle creation cycles. Partial unique index on (owner_id, series_id) for active nondeleted incomplete tasks prevents multiple active occurrences. Enabled series must have exactly one active task at transaction end; disabled/deleted series need none.

Composite same-owner foreign keys and checks cover group/category compatibility, field lengths, valid priority/frequency, completion timestamp consistency and nonnegative schedule state. Validate IANA zone membership against supported server zone names; restrict dates to a shared documented Gregorian range (recommend 1900–9999, with overflow producing a visible validation error). Index owner with change cursor, active/status/due fields and foreign keys; measure additional indexes. Use snake_case SQL, camelCase domain objects and explicit mapping.

Direct clients can SELECT authorized rows but cannot mutate domain tables, counters, receipts or history. All mutations enter a small typed command RPC. A narrowly scoped SECURITY DEFINER function is needed to write with direct table DML revoked; own it with a dedicated non-login role without BYPASSRLS, enable/force RLS on relevant tables, fix search_path and schema-qualify objects. Revoke EXECUTE from PUBLIC/anon and grant only the necessary entry points to authenticated. Check auth.uid() and JWT aal2 at entry; owner is derived, never trusted from payload. Do not use a postgres-owned definer that bypasses RLS. Keep helpers/internal tables in a non-exposed schema; expose only required RPC wrappers and RLS-protected reads. Test this privilege design against the actual Supabase stack before cloud feature delivery. Read RPCs prefer SECURITY INVOKER. Every exposed path, including metadata feeds, needs owner/AAL2 policies. Public key is safe only with these controls.

## Local model

Account database name includes project reference and owner UUID. Stores: canonical server entities, optimistic projections, immutable outbox commands, completion events, conflict records, receipts/applied results, sync metadata (cursor/schema/protocol versions) and local device metadata. Separate base and optimistic state lets incoming changes update canonical rows without erasing unsent edits. Local-only IDs remain stable through reconciliation. Operation IDs and successor/event IDs are generated and persisted once; do not generate them on retry.

One Dexie transaction records the command, its base snapshot/revision, optimistic affected rows and provisional events. Network calls never run inside IndexedDB transactions. Projection rebuild replays unresolved local commands over canonical state; a command with an invalidated base becomes a conflict instead of silently rebasing it. A second edit to the same unsynchronized entity depends on the first operation; after predecessor acknowledgement, freeze its base revision using the acknowledged result before sending. Commands are immutable once sent; payload changes require a new operation ID. Local migrations must retain unknown/pending payload versions, abort incompatibility safely and never reset the database.

## Synchronization protocol v1

Commands have protocol version, operation UUID, device UUID (diagnostic only), kind, entity identifiers, expected revisions for every existing entity read/affected, payload and client-reported event instant where applicable. Supports create/update/delete, parent deletion, complete/reopen and series configuration as explicit transactional commands. Reject arbitrary table names/patch paths, unknown versions, oversized payloads and illegal field updates. Limit request size/batch length (implemented limit one command and 256 KiB); bounded independent commands may partially succeed, but each command is atomic. Dependency order matters; do not send dependents after predecessor failure.

1. On start/focus/online/manual retry, acquire a best-effort cross-tab leader lease (Web Locks where available, IndexedDB lease fallback). Correctness relies on server idempotency, not this optimization. Verify current account generation and online AAL2.
2. Pull committed changes since the durable cursor before pushing, then reconcile pending command bases. Conflicts block their dependents, not unrelated work.
3. Submit ready commands. Server derives owner, takes the per-user transaction lock, checks receipt (owner, operation_id), compares a canonical payload fingerprint and returns the original stored result for an identical retry. Same ID with different payload is an error. Receipts include accepted/conflict/validation results; unexpected transient errors roll back and are retryable.
4. For a new command, validate expected revisions/references and domain constraints. Apply all side effects, increment affected revisions, append completion events if appropriate, allocate change sequence values and store receipt atomically. A conflict returns current canonical rows/tombstones plus a reason without applying the attempted business change. Server timestamps and command results are authoritative.
5. Client atomically incorporates acknowledgement/results into base rows, marks command resolved, rebuilds projections and unblocks dependencies. A timeout at any point retries the exact operation ID and payload. Never dequeue before durable acknowledgement.
6. Pull until caught up through a captured high watermark; commit each page and cursor in the same local transaction. Repeat after pushing. Retry transient network/5xx failures with capped exponential backoff and jitter; pause auth failures for reauthentication; retain validation errors as actionable rejected work.

### Feed ordering, bootstrap and retention

Do not paginate by updated_at or a free-running PostgreSQL sequence alone: uncommitted earlier writes can otherwise be skipped. All writes for one owner serialize on sync_state in the same transaction. Increment that owner's transactional counter under the lock; append one ordered change per affected row/event and commit before another owner-specific writer can allocate. Rollback rolls back the counter too. Every writer, including administrative repair, follows this mechanism or explicitly invalidates sync state. Read committed pages with seq > cursor and seq ≤ fixed watermark ordered ascending, using strict bounds and bounded page size (recommend 500).

Initial bootstrap starts at cursor 0 and replays the retained complete change feed into an empty canonical store; changes carry full row/event snapshots or tombstones. Cursor and page application are atomic. New writes beyond watermark arrive next round. Duplicate pulls are safe by sequence/revision. All reads are owner/AAL2 restricted. Retain changes, receipts and tombstones indefinitely in v1, so arbitrarily stale devices cannot resurrect deleted data or repeat old commands. This trades storage growth for a simple safe baseline; measure before public scale. Future compaction requires a protocol epoch, snapshot watermark and stale-device rebootstrap that preserves pending commands as conflicts; it must not silently prune replay protection. Administrative account erasure removes its retained data and invalidates sessions.

Realtime is optional wake-up optimization; reconnect always pulls the feed. Background Sync is optional, never a correctness dependency. Sync status includes last successful time/watermark, pending count and actionable errors without exposing internal payloads.

## Conflicts and deletion

Use optimistic concurrency, not clock-based last-write-wins. V1 treats any stale entity revision as a conflict, including disjoint fields, to keep semantics reviewable. Store base snapshot, user intent and current server snapshot locally. Offer keep server, apply a reviewed local version as a NEW command against current revisions, or manually merge. Rejected text remains copyable. Choosing server explicitly resolves/discards that intent; no automatic silent discard. Dependent edits are reviewed/rebased only after the predecessor resolves.

A tombstone prevents stale update/recreate; deleted identity cannot be reused. Delete-vs-edit is a visible conflict. An explicit restore command may restore a task with current revision and valid current references; deleted category/group restoration is not part of v1 (recreate with new ID). Undo deletion uses task restore; parent deletion recovery creates containers anew and requires reviewed reassignment. Parent deletion atomically touches affected assignments; concurrent moves see revisions and cannot leave dangling group/category links. Large parent cascades require limits/load testing before release, without splitting the atomic invariant silently.

## Recurrence transactions

Completion names task, series and expected revisions; server locks owner and validates active occurrence. It inserts one completion event, marks old task complete, creates the deterministic successor and updates series pointer atomically. Successor UUID derives from series ID, next occurrence date and the initiating completion operation ID using a specified, cross-runtime UUID namespace algorithm; use a vetted implementation, not security cryptography. Including the completion operation ID permits a new successor after undo without reusing a tombstoned identity. Concurrent candidate IDs are reconciled to the first committed successor. Event ID is persisted in the initiating command; unique logical completion constraint prevents multiple unreversed completion events for one completion transition.

Special case: a second completion command for an already completed occurrence returns a structured `conflict/already_completed` result referencing the canonical event/successor, regardless of different proposed successor IDs. Never overwrite the first completion timestamp. Surface different client timestamp claims in sync activity; preserve unrelated local task edits as conflicts. If the occurrence has since been reopened or series changed incompatibly, use ordinary conflict handling rather than pretending completion succeeded. Schedule edits, deletion and completion serialize with revision checks. An undo requires successor revisions and proof it is still untouched (including pending local dependents); otherwise fail visibly per SPEC.md.

Both implementations use SPEC.md's calendar algorithm, original monthly anchor, series zone and frozen completion civil date. Avoid JS Date month overflow and 24-hour millisecond increments. Prefer a small audited calendar utility; add a date library only if it materially improves correctness. Validate completion instant/zone/date consistency but acknowledge client clocks are untrusted; ordering always uses server revisions. No historical slots are synthesized.

## Authentication and threat model

Cloud authorization requires Supabase-validated JWT, owner identity and AAL2; the SPA route guard is usability only. A browser-local previously verified identity permits trusted offline access as specified in SPEC.md. Persist sessions using supported Supabase client mechanisms with account-scoped lifecycle handling; do not copy tokens into task tables/outbox or invent token encryption. Native token refresh can fail offline without erasing local work. Account identity generation guards every async callback and sync response; logout stops leases and subscriptions before clearing data. A fresh login at AAL1 must challenge before any cached task display.

| Threat                                  | Controls and limits                                                                                                                                                                               |
| --------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Anonymous, AAL1 or other-owner request  | Owner+AAL2 RLS, entry checks, minimal grants, negative SQL/API tests on every surface                                                                                                             |
| Malicious sync payload/replay           | Strict schema/limits, server-owned revisions/identity, FK/check constraints, payload fingerprint, persistent receipts and transaction atomicity                                                   |
| Lost/unlocked device                    | Logout removes cache; OS/browser locks recommended; offline cache is not encrypted and remote revoke cannot erase it                                                                              |
| Stolen session/XSS                      | MFA limits password theft, not theft of an AAL2 bearer token; restrictive CSP, no raw HTML, dependency review, HTTPS, avoid secrets in logs; session revocation effective subject to JWT lifetime |
| Account switch or late network response | Separate databases, closed prior handles, generation checks, owner checks on every local import                                                                                                   |
| Data loss/compromised hosting           | Durable transactions, quota errors, safe migrations/update prompts; host security headers, protected deployment credentials; no E2EE claim                                                        |
| MFA loss/social engineering             | No email-only bypass; approved operator verification/reset runbook or fail closed                                                                                                                 |

Use CSP compatible with built assets (avoid unsafe-eval/inline scripts), Referrer-Policy, nosniff, frame-ancestors and HTTPS/HSTS at host. Allowlist auth callback URLs; prevent open redirects. Audit logs must exclude task bodies and credentials. Client validation complements, never substitutes for database enforcement. RLS protects cloud storage, not a compromised browser or privileged operator.

## PWA and deployment

vite-plugin-pwa uses prompt updates and static precaching, with SPA fallback excluding auth/API routes as appropriate. Supabase Auth/REST/RPC traffic stays network-only; Dexie is the explicit sensitive offline store. Public shell can load unauthenticated without revealing cached tasks. ## Tradeoffs and verification sources

Revision conflicts favor visible correctness over automatic merge convenience. Per-owner serialization simplifies cursor correctness at personal-task scale; it is not a design for collaborative high-throughput workloads. Retained feeds cost storage. Date-only recurrence deliberately excludes alarms and time-of-day DST ambiguity. Local plaintext enables practical offline startup but requires explicit trusted-device expectations. No UI library/state framework is required initially.

Capabilities verified against primary documentation on 2026-10-20; exact supported package versions will be pinned in Phase 1:

- [Supabase native MFA](https://supabase.com/docs/guides/auth/auth-mfa): enrollment/challenge and assurance levels support mandatory TOTP; Taskmaster chooses to require AAL2 on every task-data path.
- [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) and [database functions](https://supabase.com/docs/guides/database/functions): authorization and transactional RPC foundations; the receipt/feed protocol is Taskmaster's design, not a built-in Supabase sync feature.
- [Supabase sessions](https://supabase.com/docs/guides/auth/sessions): access/refresh session model; trusted offline access is a Taskmaster policy.
- [Dexie API](https://dexie.org/docs/API-Reference) and [reactive queries](https://dexie.org/docs/dexie-react-hooks/useLiveQuery%28%29): transactions and observable local queries; no Dexie Cloud dependency.
- [Vite PWA guide](https://vite-pwa-org.netlify.app/guide/) and [update guidance](https://vite-pwa-org.netlify.app/guide/auto-update): asset caching/update capabilities; Taskmaster deliberately selects prompt rather than automatic reload.

## Phase 2 implemented local boundary

Phase 2 introduced historical Dexie schema version 1 in `src/data/local/database.ts`; Phase 3 extends it with v2 below. It declares tasks (local projections), canonicalTasks (empty server-state boundary), completionEvents, outbox and meta. Index definitions cover identities, owner, task IDs, task creation and unique command sequence. No database reset/populate/seed procedure runs. A future version must add an explicit upgrade transaction, preserve unknown command payloads, and abort rather than discard data. The ready guard refuses native IDB versions newer than the supported Dexie logical version (Dexie multiplies logical versions by ten). Additive-upgrade and failed-upgrade rollback tests retain task/outbox state. No historical Phase 1 database exists to migrate.

`TaskRepository` owns all reads/mutations and liveQuery subscriptions. Mutation transactions cover tasks, events, outbox and workspace metadata. IDB serializes this shared write scope across tabs; compare-and-swap on localRevision rejects stale drafts. No task-data writes appear in components. An operation generates its IDs once inside the committed transaction; a failed transaction is not a successful command and may be retried as a new local attempt. Successful outbox rows remain immutable and pending. They contain v1 intent, base/result snapshots, sequence, device/owner IDs, expected server revision and predecessor operation. The future sender must resolve dependent server revisions before first transmission; it must not treat localRevision or provisional client timestamps as authoritative cloud revisions. No replay/transport/acknowledgement machinery is implemented here.

Creation stores optional future fields as null. Recurrence configuration remains external to a task through seriesId, following the original model. Complete appends a snapshot event and updates currentCompletionId/status/completedAt atomically; reopen/undo appends a linked reversal and clears the current status/timestamp. Recompletion creates another event. Delete only sets deletedAt; restore clears it while retaining identity/current status. All historical snapshots remain unchanged. Invalid references or unsupported recurring mutations fail without writing. Server revision stays null, localRevision increments per mutation; updatedAt uses max(device time, prior updatedAt + 1ms) for stable local display metadata only.

The owner UUID and database namespace in `workspace.ts` identify a synthetic local-preview workspace, not a Supabase account. A persistent device UUID and per-workspace sequence live in IndexedDB metadata. Standard production mode cannot construct this workspace. Development/local-preview is explicitly opt-in and labeled; it must never upload its records or silently become an authenticated account database. This satisfies the plan's Phases 1–5 isolation constraint while permitting actual offline/restart testing before Auth.

The shell now uses a minimal React Router data-router root so useBlocker can guard unsaved edits on navigation. This replaces the Phase 1 declarative root solely to prevent draft loss; navigation paths, semantics and view layout remain unchanged. Drafts are transient UI state and stay mounted separately from reactive row membership, so another tab's edit/delete cannot erase an open draft. Cancel/discard is explicit; reload/close uses beforeunload protection. A cancelable local update event prevents the worker reload button from proceeding over drafts or active writes. Full cross-tab update orchestration remains Phase 9; no future migration compatibility is claimed.

Source capability references: [Dexie transactions/versioning](https://dexie.org/docs/API-Reference), [live queries](<https://dexie.org/docs/liveQuery()>) and [React Router navigation blocking](https://reactrouter.com/how-to/navigation-blocking). The local queue and revision semantics are Taskmaster's existing architecture, not a Dexie Cloud integration.

## Phase 3 organization, dates and schema v2

`TaskDatabase` retains the original schemaV1 declaration and adds schemaV2 with categories/groups, canonicalCategories/canonicalGroups and task indexes for categoryId, groupId and dueDate. This is an additive Dexie `version(2).stores(...)` migration: it creates stores/indexes without a row-rewrite callback because no existing record shape needs transformation. Tasks, tombstones, completion events, metadata and even legacy/unknown v1 queue payload fields remain untouched. The newer-schema guard now rejects native versions above 20. Canonical organization stores, like canonicalTasks, remain empty until actual cloud integration; no speculative receipts, feed or server client were introduced.

Category and Group models use stable UUID/owner, name, creation/update timestamps, tombstone, nullable server revision, localRevision, provisional flag and lastOperationId; Group requires categoryId. OrganizationRepository owns container mutations; TaskRepository still owns every task mutation and the one shared live workspace subscription. Both use the same IndexedDB database and transaction scopes including categories, groups, tasks, outbox and metadata. Same-owner/live-parent validation and duplicate sibling-name checks run under the read-write lock, so separate tabs cannot race a move past deletion or create accidental duplicates. No UI component writes IndexedDB.

Task assignment rules: group-only input infers its existing parent; explicit mismatched pairs fail. Changing category without a compatible explicit group clears the group. Clearing category clears group. Restore validates current references. Category deletion captures all affected records, tombstones live child groups and clears task category/group assignments, including task tombstones. Group deletion clears task group assignments and retains category. Cascades increment local revisions and use the same operation ID for every affected projection, preserve completion history, and commit with exactly one outbox insertion and metadata increment. A failure at any point rolls back the complete cascade. Stale task/container editor bases are rejected with their UI draft retained. No silent merge is introduced.

`localCommands.ts` is the shared transaction-only command appender, not a sync engine. New local outbox serialization has protocolVersion 2 and adds changes (every affected entity’s base/result), reads (kind, ID, server/local revision and predecessor operation) and deduplicated dependencies. Unchanged destination parents are included in reads/dependencies. Primary base/result/dependsOn fields remain for diagnostics and predecessor compatibility; multi-entity correctness uses the complete arrays, not only the primary record. The table’s sequence remains unique and transactionally incremented. Schema migration never upgrades/relabels/replaces old v1 command objects; new operations can depend on their unchanged IDs. The future Phase 8 sender must decode both local envelope versions, freeze dependent server revisions before sending, validate duplicate-name constraints on the server and translate them to the approved wire RPC contract. No second transport, acknowledgement, retry, replay or server protocol was implemented.

`LocalTasks` remains the single task interaction controller for Big List, Category and Date routes, with shared TaskForm/TaskRow, history, undo, failure reporting and draft guards. CategoryTree and DateGroups are projections of that subscribed state; they hold no independent task copies. OrganizationForm shares the existing dirty-draft guard. Category/group Add task buttons set an explicit creation target and focus the quick form. Native details/summary provide keyboard-accessible disclosure; confirmed deletion and asynchronous persistence retain focus within the view. The shell, paths, identity harness and production boundary remain unchanged.

`domain/dates.ts` validates Gregorian date-only deadlines independently of browser parsing and performs instant-to-civil-day grouping through Intl.DateTimeFormat with an explicit time zone. Stored deadlines are never passed through Date parsing for display or grouping. DateGroups sorts ISO civil keys chronologically with undated tasks last and marks active overdue groups. Creation/completion grouping uses the current device zone; completion mode includes current completed tasks, not reversed historical events. The separate event ledger remains intact. Focus/visibility refresh plus a one-minute timer handles day/zone changes without adding filters or recurrence scheduling. Deterministic tests cover leap/century dates, DST and midnight boundaries; browser date tests use America/Los_Angeles.

Tradeoffs remain explicit: local snapshots/read sets increase queue size; parent deletion is intentionally one atomic transaction and has not yet been certified for arbitrarily large cascades. Name comparison is NFC plus lowercase rather than full locale-dependent case folding. No organizational restore, account access, cloud constraints, new dependency, advanced filtering or configurable sorting is included.

## Phase 4 shared query implementation

`domain/query.ts` owns FilterSpec version 1, defaults, validated preference decoding, date bounds, hierarchy diagnostics, effective status and the single pure filter/sort operation. It consumes subscribed current task projections and an explicit civil today/time-zone context; it does not read IndexedDB, write records, fetch data or inspect completion events. All predicates combine with AND, with explicit null/all selections. Date-only comparisons and a reusable Intl civil-date formatter keep deadline and instant semantics distinct; calendar offsets use UTC calendar setters solely as a Gregorian calculator, never elapsed-day millisecond subtraction. Sort uses normalized keys, null-last deadlines, documented priority ranks and final code-unit UUID ordering.

`features/query/useTaskQuery.ts` loads current view preferences, memoizes results against snapshot/query/day/zone/recovery mode, repairs deleted organization references with notice after a real snapshot arrives, and refreshes calendar context on resume/focus or minute ticks. Unchanged day/zone reuses state; draft/error/checkbox-busy changes do not rerun queries. Search/filter/sort changes reuse the existing reactive workspace snapshot and never trigger another repository scan. Actual task/organization mutations still trigger the existing transactional liveQuery read. `QueryControls` is shared by every LocalTasks route; CategoryTree and DateGroups only project the ordered results. Date grouping no longer independently re-sorts rows. Empty containers remain available for management and counts reflect shown results. CompletionHistory memoizes the independent event ledger, builds reversal title lookup once per event snapshot, and renders event rows only while expanded, avoiding repeated quadratic history searches during typing.

`features/query/preferences.ts` stores small JSON values in localStorage, scoped by database namespace, owner and view, with a v1 key suffix and payload version. Only preferences use localStorage; tasks/history/outbox remain exclusively IndexedDB. Parsing validates every field and rejects unsupported versions, malformed dates/types and unknown enum values; known values are copied without unknown keys. Invalid preferences reset with notice, not task deletion. The current edit-date-field tab/disclosure state is transient; each field's actual range, statusExplicit, date grouping, search and sort persist. Storage denial/quota feedback applies in-memory preferences for the current visit. Separate tabs keep independent mounted controls (no live preference propagation); a later mount/reload reads the last saved preference. Future authenticated use must open/read these keys only after the existing account/AAL2 boundary; the synthetic namespace never becomes a real account. Search terms are not encrypted and should be treated as browser-local content.

No IndexedDB schema or migration change: schema v2, existing rows and v1/v2 outbox entries are untouched. Priority edits use TaskRepository's existing validation and atomic transaction, carrying the optional low/normal/high/null field into v2 commands and later completion snapshots. Omitted priority preserves the value. UI Medium maps to normal, with no second enum or rewritten historical commands. Completion-mode status defaults use explicit intent metadata rather than mutating status on grouping changes. All other architectural decisions remain unchanged.

Query cost is O(n + k log k) for n current records and k matches, with at most three civil-date conversions per candidate and normalized sort keys computed once. Extra memory is O(k); no search index/library/worker/virtualization is introduced. The current repository still reads full task/history/outbox snapshots after mutations; this phase avoids adding scans during query interaction rather than claiming arbitrary collection scaling. Opening very large unvirtualized lists/ledgers and large parent cascades remain measurement risks. Query microbenchmarks are distinct from full DOM render and mobile latency certification.

## Phase 5 local recurrence implementation

Dexie schema v3 adds recurrenceSeries and canonicalSeries plus a tasks.seriesId index. The existing v1 and v2 store declarations remain unchanged. Additive version(3).stores(...) creates stores/indexes without rewriting any legacy task, event, organization record, metadata or outbox payload (including unknown fields). Legacy standalone tasks already have null seriesId/occurrenceDate, so no row transform is necessary. The newer-schema guard now refuses native versions above 30. canonicalSeries remains empty; no remote adapter, receipts/feed, SQL or account boundary is implemented. Real browser tests migrate native v2 and retain all nine old stores exactly; the v1 migration regression remains covered. Future upgrades must add versions rather than edit applied schemas.

`domain/recurrence.ts` defines RecurrenceSeries (UUID/owner, frequency, anchorDate, IANA timeZone, template title/description/priority/category/group, activeTaskId, enabled, scheduleRevision, revision/localRevision/provisional timestamps/tombstone/operation metadata). Task retains seriesId plus occurrenceDate, and each new occurrence is a separate task record. Domain nextOccurrence uses explicit Gregorian integer fields: Daily increments civil date; Weekly uses the anchor's Gregorian weekday; Monthly compares clamped candidates while preserving anchor day. It skips directly past the greater of occurrence date and completion date, not by generating missed slots. Calendar calculation is pure, bounded and independent of the runtime display zone. `tests/fixtures/recurrence.ts` preserves cross-runtime fixtures for future SQL parity.

Successor/reanchor UUID rule: UUID v5, RFC URL namespace, UTF-8 name equal to JSON.stringify(['taskmaster','occurrence',1,seriesId,nextDate,operationId]). Series IDs and operation/event IDs remain stable UUIDs generated once inside a successful transaction. Including operationId prevents reusing an undo-tombstoned identity. Pinned uuid 14.0.3 supplies the vetted synchronous name-based algorithm ([official API](https://github.com/uuidjs/uuid#uuidv5name-namespace-buffer-offset)); no custom hash/authentication cryptography was added. Native randomUUID alone cannot satisfy deterministic cross-runtime name derivation. uuid has no runtime dependency tree; only consumed exports enter the bundle. This adds a small hashing/UTF-8 implementation and ordinary package supply-chain exposure, not a network service or general recurrence framework. The install also detected an existing serialize-javascript build-tool advisory; its compatible 7.1.2→7.1.4 patch was applied in the lockfile, with zero audit vulnerabilities afterward.

TaskRepository remains the public task use case/repository for every view. Transaction-only `data/local/recurrenceMutations.ts` owns series loading/configuration, advancement, undo guards and invariant checks; it does not start a second database, queue, transaction manager or scheduler. Every task write now includes the series store in its shared IDB write scope. A successful write checks one live incomplete linked task for each enabled affected series and no linked incomplete tasks for a disabled one. Stable IDB transaction scopes serialize cross-tab races; all supported writers obey the invariant. OrganizationRepository also touches affected series templates in the same existing deletion cascade and command, clearing group/category references on active and disabled templates while preserving historical snapshots. Restore/explicit standalone conversion detach incomplete tombstones instead of reviving a second active link.

The existing local v2 command envelope is extended with the typed series entity kind, optional recurrence input and reopen-standalone intent. No legacy envelopes are relabeled or rewritten and no wire RPC change is claimed. Read sets capture task, series, successor (for undo) and assignment parents with server/local revisions and predecessor IDs. Changes contain every task/series base and result: completion has old task, successor and series; undo has reopened task, successor tombstone and series; reanchor has retired task, replacement and series; creation/configuration/deletion/organization commands include their complete effects. One event and one outbox command/sequence commit with each completion or reversal; failure rolls back every store. Future senders must decode the old commands as well as these schema-v3 intents and freeze dependent server revisions before transmission.

New recurring completion events extend the existing immutable completion variant with recurrence facts: series/occurrence/successor IDs, successor date, frequency, anchor, zone, effective completion date and schedule revision. Existing events need no new fields. The frozen occurredAt is the actual client-reported completion instant; conversion to the series-zone date and successor date is stored once. Provisional updatedAt can still be clamped monotonically for display metadata, but it never substitutes for that event instant or decides conflicts. The future server must validate event instant/zone/date consistency and reproduce the same calendar and UUID rules.

Local duplicate completion recognizes the original frozen base revision and its retained command/event while the current series transition remains unchanged, returning its existing completed task without inserting anything. After reversal/recompletion or incompatible edits, stale revision checks reject the attempt. This is not a cloud idempotency receipt implementation. In two independent offline databases the same logical series/task/occurrence may yield different operation-specific candidate IDs, timestamps and dates; both commands survive. The Phase 6/8 server handler must lock owner, check operation receipt/fingerprint and revisions, preserve the first committed completion timestamp/event/successor, return already_completed only for a still-compatible completed occurrence, and surface incompatible/reopened/schedule-edited states as conflicts.
