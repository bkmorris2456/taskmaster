# Taskmaster implementation plan

Status: Phase 6 implementation and local native Supabase certification completed. Stop after Phase 6; Phase 7 requires approval. Each phase is a reviewable delivery unit, not permission to implement later phases. Phase records below distinguish implemented commands and validation from future proposals.

## Sequence and shared gates

Retain the proposed ten-phase sequence, but define protocol/types and recurrence fixtures early; schema/security must precede real cloud auth/data use. Phases 1–5 are local development with isolated synthetic data only. No fake-auth bypass may reach a deployed production build. Phase 7 must not expose real task data before RLS/AAL2 gates pass. Phase 8 is the main correctness gate, not a Realtime integration exercise.

Each phase requires an inspected diff, updated docs, meaningful tests, passing typecheck/lint/build where available, documented manual checks and a concise report of results/limitations. No phase is complete with failed required checks. Reassess package compatibility using official sources at installation; commit one lockfile. No production resources or deployments until authorized.

Proposed npm scripts become verification contracts in Phase 1: `typecheck` (tsc without emit), `lint`, `test` (Vitest non-watch), `build`, `test:e2e` (Playwright). Later add `test:db` for migrations/SQL/API integration against local Supabase and `test:sync` for deterministic protocol integration. Use `npm ci` in clean CI once a lockfile exists. Supabase CLI and local containers are development tools, not a custom backend. Use `supabase start` and `supabase db reset` only against clearly identified disposable local environments; never reset remote data.
