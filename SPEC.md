# Taskmaster product specification

Status: Phase 6 explicitly authorized; database foundation implemented and locally native-Supabase certified. Local task organization and all three views are available in the isolated development/local-preview workspace; full product requirements below remain staged. ARCHITECTURE.md defines the protocol; IMPLEMENTATION_PLAN.md defines delivery gates; AGENTS.md governs engineering. Recommendations below are the proposed v1 defaults, not permission to expand scope.

## Goals and boundaries

A fast, minimal personal task manager with checkboxes, dependable offline work and cloud synchronization across devices. React, strict TypeScript, Vite, Tailwind CSS, Dexie/IndexedDB, Supabase Auth/PostgreSQL, native TOTP MFA, vite-plugin-pwa, Vitest and Playwright are the baseline. Deploy a static SPA to Cloudflare Pages or equivalent; PostgreSQL functions provide transactional commands without a separate backend.

In scope: tasks, optional categories/groups, three task views, composable filters, history, daily/weekly/monthly recurrence, authentication, conflict resolution and installable offline operation. Out of scope: collaboration, shared workspaces, subtasks, attachments, reminders/notifications, calendar integration, AI, billing, rich text, custom recurrence expressions and saved-filter UI. Preserve an extensible filter value format without implementing saved presets.

## Data contract

All business entities use UUIDs and an immutable owner ID referencing auth.users. UUIDs are generated on clients for offline identity. Cloud rows have positive integer revision, server-controlled created_at/updated_at UTC instants and nullable deleted_at tombstones. Local provisional timestamps are marked provisional; never use client clocks for conflict ordering. Display timestamps may settle after synchronization.

| Entity            | Product fields and rules                                                                                                                                                                                                                                                               |
| ----------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Category          | name, 1–80 trimmed characters                                                                                                                                                                                                                                                          |
| Group             | name, 1–80 characters; required category_id                                                                                                                                                                                                                                            |
| Task              | title, 1–240 trimmed characters; optional plain-text description up to 10,000 characters; completed boolean; nullable completed_at; nullable due_date (ISO civil date); nullable priority (low/normal/high); nullable category_id and group_id; nullable series_id and occurrence_date |
| Recurrence series | template title/description/priority/category/group, frequency daily/weekly/monthly, anchor_date, IANA time_zone, schedule revision, active_task_id, enabled flag; interval fixed at one                                                                                                |
| Completion event  | immutable ID, task_id, optional series_id/occurrence_date, completed_at, reporting time zone, task title/metadata snapshot, originating operation ID; reopen/undo adds a linked reversal event rather than destroying history                                                          |

Completed status and completed_at must agree. No group without its category; a task's group must belong to its category and owner. Same-owner composite foreign keys enforce ownership relationships. Deleted parents cannot receive new assignments. Priority null means unspecified, distinct from normal. Dates are date-only, not midnight UTC timestamps. Task history is derived from events; current completed task state supports filters. Deleted tasks disappear from normal views; completion snapshots survive task deletion. No hard purge in v1 except explicit administrative account erasure.

Deleting a group clears group assignments. Deleting a category tombstones its groups and clears category/group assignments; tasks and history survive. Each is one atomic command, locally and on the server. Moving a group between categories is out of scope. Moving a task into a group sets its category; changing category clears an incompatible group. Deleting a recurring active task also disables its series; historical events remain. Deleting an old occurrence does not disable the current series.

## Workflows and views

Quick add requires only title: Enter saves and keeps capture ready; Escape cancels. Optional metadata uses progressive disclosure in a compact editor. All edits persist locally before success feedback. Checkboxes complete; history offers reopen. Provide an announced Undo action for at least 10 seconds plus persistent history actions. Delete is explicit and reversible through a recovery action until resolved; a tombstone is not a completion. Unsynchronized, rejected and conflicting items remain discoverable.

Category view includes uncategorized, category-level tasks and groups, including empty containers. Rename/create/delete containers inline. Counts show completed/total nondeleted current task records under the current filters; recurring history does not inflate counts. Default active view can show 0 completed because the status filter applies; label counts accordingly.

Date view defaults to due_date ascending with overdue (before today and active), today, future calendar-date groups and a no-due-date section. Switch to creation or completion dates. Creation/completion instants group using the device's current display time zone; completion grouping includes only completed task records, with reversed completions excluded. A separate history list shows every completion event, including recurring occurrences. Completed tasks are hidden by default in all primary views except Date view’s Completion date mode, which defaults to completed task records until the user explicitly selects a status. Explicit Active stays selected and yields no completion-date rows.

Big List combines all nondeleted tasks. Status active/completed/all, filters, sorting and search apply identically across views. History is reachable from primary navigation or status controls without creating a dashboard. Navigation consists of Category, Date, Big List and a compact account/sync menu.

## Filters and sorting

Use a serializable, versioned FilterSpec; predicates across fields combine with AND, selected values within a field with OR. Empty selection means no restriction; explicit null selection means uncategorized/no group/no due date/no priority. Group/category selections must be compatible, with impossible combinations visibly producing no matches. Search is case-insensitive substring matching over title and description, with a documented Unicode normalization policy; no remote search required.

Support status, category, group, created/due/completed date ranges, priority and text. Today/yesterday are civil days; last N days includes today and N−1 preceding days for 7/14/30. Custom ranges include both selected civil dates; timestamp comparisons use [start-of-first-day, start-of-day-after-last) in display time zone. Null dates do not match ranges; explicit no-date filter handles them. Recompute relative dates on midnight, resume and zone change. Date filters use current task fields, not every historical event; history can apply the equivalent filters to event snapshots.

Sort newest/oldest by created_at, title ascending/descending by normalized text, due date ascending/descending, priority high→normal→low→unspecified, status active before completed. Null due dates sort last in either direction. UUID ascending is the final stable tie-breaker. Initial default row sort is newest first; Date view always orders date groups chronologically, with configurable row sorting inside groups. The default application route opens Big List. Saved filter UI is deferred.

## Recurrence and history

Recurrence is a series plus individually identified task occurrences. Exactly one nondeleted incomplete occurrence exists per enabled, nondeleted series in an authoritative database. Offline replicas may temporarily disagree but must reconcile to that invariant. Completed occurrences and immutable completion events remain accessible.

A recurrence requires a starting due date and captures the device's IANA zone. Daily advances by calendar days; weekly by seven days from anchor; monthly uses the original anchor day, clamped to the month's last day, restoring the anchor later (Jan 31 → Feb 28/29 → Mar 31). No time-of-day recurrence: DST never changes the scheduled civil date. Gregorian calendar rules apply.

Completing an occurrence generates one successor at the earliest schedule date strictly later than both its occurrence_date and the completion's effective civil date in the series zone. Thus an overdue task stays as one active item until completed, then missed slots are skipped without fabricated completion records. Example: daily Oct 1 completed Oct 5 generates Oct 6. Future tasks completed early advance to the next scheduled date. No background timer generates occurrences. occurrence_date is the immutable schedule identity; editing an active task's displayed due date alone does not reanchor the series or change occurrence_date. Reanchoring requires the recurrence editor. Edits to recurrence affect the active task and future template only, preserve past snapshots, and require series revision checks. Changing schedule reanchors to the explicitly chosen new starting due date by atomically retiring the uncompleted occurrence and replacing it with a new task identity; its prior occurrence_date is never overwritten. Disabling recurrence leaves the current occurrence as a standalone task.

Offline completion freezes its client-reported instant and derived series-zone civil date in the command. The server validates consistency and applies the same calculation rather than substituting receipt time; clock mistakes may affect scheduling and are correctable by editing the active date. Simultaneous completions of the same occurrence yield one completion and one successor; the first committed completion's timestamp wins, and differing later timestamp claims are visible in sync activity. No duplicate history event is created.

Undo/reopen of a recurring occurrence atomically reverses its completion and removes its untouched generated successor, reopening the original. If the successor has been edited, completed, or has dependent operations, reject the automatic reversal with an actionable conflict; offer reopening the old item as a standalone task after explicit confirmation. Never create two active occurrences for one series. Reopening an ordinary task adds a reversal event; completing again creates a new completion event.

## Authentication and offline access

Online onboarding: register email/password → verify email → sign in → enroll and verify TOTP → AAL2 → open task data. Existing users challenge a verified factor as needed. Persistent Supabase sessions use native refresh handling. Password recovery uses allowlisted redirect URLs, does not remove MFA, and still requires AAL2 for task access. Factor removal must not become an AAL1 data bypass. Secure logout stops workers, clears in-memory state, locally invalidates access immediately, removes the account database and tokens, and attempts server session revocation online. If pending changes exist, explain that logout will erase them and require confirmation or cancel; offline logout cannot guarantee remote revocation.

Only a previously online AAL2-verified account on this browser may reopen its local database offline. Expired access tokens do not erase or freeze that local workspace: edits queue with a visible authentication-needed status. No cloud calls until session refresh and, where necessary, renewed MFA produce AAL2 for the same account. Explicit logout or a confirmed revocation/account mismatch locks the workspace; never upload its operations under another identity. A network failure is not proof of revocation. Offline revocation cannot be detected. This is a trusted-device convenience, not local encryption or an offline MFA verifier.

Use a separate IndexedDB name per Supabase project and user UUID. Only open it after selecting the matching authorized local identity. On account switch, close and hide the prior database, cancel requests and discard late results using an identity generation token. A fresh AAL1 login cannot unlock an existing cache. Local data is accessible to someone controlling an unlocked browser profile; document device locking and storage loss risks.

Recovery recommendation: encourage a second native TOTP factor if supported by the configured Auth release; verify this before exposing enrollment. Do not promise native recovery codes or treat Supabase dashboard MFA documentation as end-user Auth behavior. With no usable factor, default to fail-closed access. A production recovery procedure requires an approved operator runbook: independent identity verification beyond email/password alone, audited privileged factor reset, session revocation, user notification and mandatory reenrollment before data access. No reset API or privileged key in the SPA. Recovery policy is a release-blocking decision; initial delivery can explicitly offer no self-service lost-factor recovery.

## Offline and synchronization requirements

IndexedDB is the immediate working store; local mutations and durable outbox insertion share one transaction. Local failure means no success indication. Task/category/group CRUD, recurrence, history, filters and search work without network after initial authentication and app caching. Queue survives reloads and browser restart subject to browser storage retention. Request persistent storage where available; explain private browsing, eviction and quota limitations. Never promise recovery of local-only work after storage removal.

ARCHITECTURE.md's revision-checked commands, idempotency receipts, serialized per-user change feed, tombstones and explicit conflict resolution are mandatory. Realtime may wake the sync loop but is not a source of guaranteed delivery. Show offline, pending count, syncing, synced, authentication needed, conflict and error states. “Synced” means no pending commands and caught up through the last successful server watermark, not knowledge of all future changes. Retries must not discard user intent.

## Security and quality

RLS must require owner = auth.uid() AND JWT aal = aal2 for every task-data access, including history, changes and receipts. Commands require the same conditions independently. See threat model in ARCHITECTURE.md. Validate client input for feedback and enforce server limits, ownership, references and invariants independently. Never render raw HTML descriptions; never log tokens, TOTP secrets or task content. Only Supabase URL and publishable/legacy anon key belong in VITE_*; privileged credentials belong only in protected operator/CI contexts. No authenticated API responses in service-worker caches.

Dark default, monospace system font stack, compact rows with generous hit targets, subtle borders and restrained accent. Native labeled checkboxes/buttons, visible focus, predictable tab order, keyboard quick-add and navigation with discoverable shortcuts that avoid input conflicts. Meet WCAG 2.2 AA: contrast, non-color status cues, screen-reader announcements, reduced motion, reflow at 320 CSS pixels and 200% zoom; target 44px touch controls with at least WCAG minimum spacing/size. Preserve focus when completed rows disappear and expose undo accessibly.

Performance targets to verify on a declared midrange mobile profile: local mutation feedback p95 <100ms, filter/search p95 <200ms for 10,000 task records plus 20,000 history events, offline shell usable within 2s of warm launch. Initial JS target ≤200 KiB gzip excluding icons; measure before adding dependencies or virtualization. Sync in bounded pages and batches without blocking input. These are provisional engineering budgets, not measured claims.

PWA: HTTPS, manifest with standalone display/start URL/theme/name, 192/512 icons including maskable assets, versioned static precache and navigation fallback. Confirm offline readiness before claiming installed/offline-capable. Prompt for updates; commit local work and pause sync before coordinated reload, never force activation or clear IndexedDB. Migration failure must preserve the old database and offer recovery. No promise of background sync while browsers suspend the app; foreground start/focus/connectivity/retry triggers guarantee eventual attempts.

## Release acceptance

- Title-only capture, edit, completion, undo/reopen, deletion and movement work online and offline; reload preserves pending work.
- All three views, counts, null fields, date presets, sorting and search agree on shared semantics.
- Leap years, month ends, DST, missed dates, early completion and simultaneous devices preserve recurrence/history invariants.
- Lost responses, duplicate commands, concurrent edits, parent deletion and interrupted paginated pulls cause no silent loss or skipped changes.
- Anonymous/AAL1/other-user API and RPC attempts fail; verified AAL2 owner succeeds; logout/account switching prevent UI or cache mixing.
- Installed app starts offline; updates/migrations preserve queued work; keyboard, touch and accessibility checks pass.
- Tests and documented deployment/recovery procedures in IMPLEMENTATION_PLAN.md pass before release.

## Phase 2 scope clarification

Before authentication exists, local CRUD uses an explicitly labeled synthetic test workspace enabled only in development and the opt-in local-preview build. Standard production builds cannot open it. This implements the existing plan's isolated-development rule; it is not an exception to mandatory MFA for eventual real account data. No automatic transfer of synthetic records into authenticated accounts is authorized.

Phase 2 Big List provides active/completed/deleted status access, title/description editing, complete/reopen, completion undo, deletion restore and an append-only completion ledger. Other filters, sorting controls, categories, date behaviors and recurring configuration/scheduling remain deferred. Recurrence is reserved through nullable series_id/occurrence_date references rather than a second embedded configuration source. Completion snapshots survive reopen, edit and deletion; the Deleted recovery view exposes tombstones without permanent purge.

A localRevision detects stale concurrent local mutations, separately from a nullable unacknowledged server revision. All local timestamps are provisional UTC instants. The durable unsent outbox starts with the first mutation; its count is not a claim of cloud synchronization. Undo is offered without a timer while this view stays mounted; reopening via Completed remains available after restart. Storage errors preserve records and current drafts rather than reset the database. Unsaved in-memory drafts have discard/reload protection but are not promised to survive a forced process kill.

## Phase 3 product clarification

Categories and groups now support create/rename/delete in Category view. Names are trimmed, limited to 80 UTF-16 code units, and compared with Unicode NFC normalization plus default lowercase: live category names must be unique within an owner; live group names must be unique within their category. A deleted name may be reused with a new UUID. No group can be moved between categories. Organizational deletion requires explicit confirmation; it does not complete or delete any task.

Deleting a category tombstones its live groups and clears category/group assignments on every assigned task, including completed and already-deleted tasks, so later task restore cannot resurrect an invalid reference. Deleting a group clears only its group assignment; its tasks stay in the parent category. History snapshots are never rewritten by either operation. Category/group restore is not supported; recreate with new IDs as specified above.

Task editors support optional category/group and date-only due date. Choosing a category clears the prior group; selecting an existing group through repository commands can infer its parent, but an explicitly mismatched category/group pair is rejected. Selecting Uncategorized clears both assignments. All relationships are rechecked transactionally against live, same-owner records. Scoped Add task actions preselect the category/group without creating a second task model.

Category view includes empty expandable categories/groups, direct category tasks and Uncategorized. Counts are completed/total nondeleted task records under the current status selection, labeled “shown”; completion events do not inflate them. Active defaults therefore show zero completed among shown tasks. Completed and Deleted remain accessible, and shared completion/edit/history behavior works in each primary view.

Date view defaults to chronological due-date groups, with undated tasks last and overdue labels only for active tasks before the current local day. Creation and completion instants group by the current display time zone; deadlines remain validated Gregorian YYYY-MM-DD strings (1900–9999), never midnight UTC instants. In Phase 3, completion date mode automatically selected completed records; Phase 4 refines this default to preserve explicit status choices as described below. Reopening removes the task from completion grouping without erasing its ledger. Relative day labels refresh on focus/resume and within one minute after midnight. Date presets/range filters and configurable sorting are not part of Phase 3.

## Phase 4 query semantics

One versioned FilterSpec and pure query engine serve all three views. Status defaults to Active; Completed and All are explicit choices. Deleted remains a separate recovery mode, ignores the status predicate, applies the other filters, and is not restored as a view preference. Completion-date grouping defaults to Completed only while statusExplicit is false. Selecting any status persists that explicit choice across grouping changes/reload: Active yields no completion-date rows with an explanation; All includes only currently completed rows in those groups. Reset restores the initial query, including due-date grouping and implicit Active. This refines Phase 3's unconditional automatic status switch as required by Phase 4.

Each category/group/priority control selects one value; all dimensions combine with AND. All categories/groups impose no restriction; Uncategorized and No group match null assignments. A category plus No group means direct category tasks. Specific group with All categories is allowed. The UI limits group options to the selected live category and clears the group filter when category selection changes; malformed incompatible pairs produce an explicit error and no matches. Deleted/missing references are cleared once the real workspace loads, with visible notice; preferences for unmounted views are repaired when next opened. These repairs never change task assignments or add commands. Named presets and multi-select controls remain outside this phase; the value contract is versioned for later extension.

Created, Due and Completed each retain an independent range; the date-field selector edits one range without clearing the others. All dates imposes no restriction; No date explicitly selects null (created timestamps always exist, so Created + No date has no matches). Presets Today, Yesterday, Last 7/14/30 Days include both endpoints; Last 14 Days includes today and the preceding 13 civil days. Custom requires two valid dates with start ≤ end; incomplete/reversed ranges show feedback and no matches. Instant fields are converted to civil dates in the current device zone before inclusive comparison, equivalent to local-day half-open instant bounds, including DST. Due strings are compared directly, never converted to UTC. Relative days/zone refresh on focus/visibility and within one minute of midnight. No separate time-zone setting is introduced.

Completed-date predicates use current completedAt, not historical snapshots. Reopened tasks have null completedAt, so fail dated completion ranges and match No date if their status also matches. The independently labeled completion ledger remains unfiltered and retains all snapshots/reversals. Sorting occurs within Category/Date groups without changing container or chronological group order. Newest/oldest use createdAt; title keys use NFC plus default lowercase and deterministic code-unit comparison (not locale collation); priority is High → Medium → Low → unspecified; Medium labels persisted normal. Status sorts active before completed. Null deadlines remain last in both directions; UUID ascending breaks every tie. No underlying rows are mutated.

Search trims outer whitespace and matches an NFC-normalized, default-lowercase substring of either title or description; internal whitespace is literal and diacritics remain significant. Empty/whitespace-only search is unrestricted. Minimal optional priority editing uses existing forms; no schema migration is needed because nullable priority already exists. Preferences (including search terms) are plaintext, local, per view/workspace, version-validated and separate from task data; storage failures retain usable in-memory controls with feedback. No cloud preference synchronization or outbox writes occur.

## Phase 5 recurrence behavior

Daily, Weekly and Monthly are the only recurrence frequencies; interval is one. The compact Repeat selector is part of the existing metadata editor. Enabling requires a valid starting anchor date (1900–9999) and a supported IANA zone, initially the device zone; enabling sets the current due date to the anchor. Weekly uses the anchor weekday; Monthly uses its original day-of-month with last-valid-day fallback. The saved series zone stays fixed when the device/display zone changes. The editor previews the date after completion today; the current active row shows its scheduled date and due date. No clock tick or app launch generates or advances occurrences.

Completing preserves the completed occurrence and its immutable snapshot, creates exactly one incomplete successor, advances the series pointer and appends one durable command in the same transaction. The successor is the first scheduled civil date strictly after max(current occurrence_date, completion's series-zone civil date). Missed dates are skipped without history entries; completing early still advances beyond the existing scheduled occurrence. Gregorian field arithmetic handles leap centuries, month/year boundaries and DST without elapsed-day duration arithmetic. Date overflow rejects the whole command and preserves the task; reschedule or disable recurrence to proceed.

Ordinary edits to the current recurring task update its future template. Editing its due date alone does not change the occurrence identity or monthly/weekly anchor. An explicit frequency/anchor/zone change increments scheduleRevision, tombstones the current incomplete task and creates a replacement occurrence with a new UUID in one command; the series ID stays stable. Past completion snapshots are never rewritten. Historical completed task metadata can be edited, but cannot reconfigure the live schedule. Disabling detaches the current task as standalone and disables the old series. Later enabling creates a new series. Deleting the active occurrence also disables/tombstones its series; deleting a completed historical occurrence does not disable the current series. Restoring any incomplete recurring tombstone is explicitly labeled “Restore as standalone” and detaches it, so undo-generated or reanchored tombstones cannot become a second active occurrence. Completed restored records keep their historical link and guarded reopening rules.

Undo/checkbox reopen of a recurring completion is allowed only when its generated successor is still the active pointer, incomplete, nondeleted and untouched, the series has not changed, and no later command depends on that completion/series/successor. It appends a reversal, tombstones the generated successor, restores the original occurrence and advances revisions atomically. Recompletion has a fresh operation and successor UUID, preserving the earlier tombstone and events. A persisted edit/save, reassignment, schedule change, later completion or other dependent command blocks automatic undo with an explanation. Completed recurring rows also offer “Reopen as standalone”, requiring explicit confirmation; that appends a reversal and detaches the same historical task without changing the current series. No silent fallback or duplicate series occurrence is permitted.

Same-browser repeated completion attempts using the same frozen occurrence revision return the existing completion while its series transition remains unchanged; no extra event, successor or command is inserted. Stale attempts after undo, editing or a later transition fail visibly rather than advance again. Independent offline replicas can each retain a candidate successor/event and command for the same logical occurrence. Phase 5 does not reconcile them: the future server must apply ARCHITECTURE.md's serialized first-commit/idempotency rule, return the canonical event/successor and preserve incompatible edits as conflicts. This phase's tests cover retained candidates and local invariants, not server convergence.

## Phase 6 cloud contract clarification

The normalized cloud schema and transactional command infrastructure are implemented without activating cloud access in the application. Every task-data surface requires owner plus AAL2, including history, changes and receipts. Direct client writes remain revoked; only validated RPC commands mutate data. Local native Supabase/Auth assurance and gateway integration are verified; real application data still requires Phase 7 account boundaries.

Conflicts preserve user intent: stale or deleted entities return canonical state/tombstones; missing or inaccessible references return kind/id and null state without revealing another owner's data. A compatible competing recurring completion returns conflict/already_completed with the first event/successor and timestamp disagreement information, rather than fabricating success or advancing again. Validation and conflict receipts are retained; reviewed replacements require new operation IDs.

Initial synchronization omits cursor or explicitly supplies zero. Explicit null cursor is rejected; omitted/null watermark captures a committed owner boundary. Pages retain that boundary and a contiguous ordered checkpoint. Tombstones, events and receipts are retained indefinitely in v1. The cloud foundation does not change local task behavior, IndexedDB schema v3 or completion history. Implementation/API/setup/security details are in ARCHITECTURE.md and docs/SUPABASE.md; exact verification and remaining blockers are in IMPLEMENTATION_PLAN.md. No Phase 7 UI or Phase 8 sender is implemented.
